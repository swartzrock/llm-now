03 / Reusable workflow

Shortcut creation moves before the first model call.

The new sequence commits the user’s reusable target before work begins. The first prompt then proves the shortcut instead of deciding whether to save it afterward.

Old behavior
run → maybe save
  1. 1Choose provider and modelThe launcher starts with selection mechanics.
  2. 2Enter promptThe user must have work ready now.
  3. 3Generate responseThe model call completes first.
  4. 4Optionally name an aliasReusable setup appears as a postscript.

Cost: a failed or abandoned run never reaches the reusable setup decision.

New behavior
save → prove it
  1. 1Create a new shortcutThe intent is selected at the root.
  2. 2Choose provider and modelThe target is selected in context.
  3. 3Name and save shortcutThe durable receipt appears before any model call.
  4. 4Enter its first promptOne generation immediately verifies the saved target.

Improvement: the shortcut survives cancellation of its first prompt and is ready for the next invocation.

SC-02: save before first promptStorage remains provider + model only.

05 / API-key onboarding

A credential enables a provider; the shortcut selects a model afterward.

The new flow makes the data model visible: one provider credential can support many models and many shortcuts. The key is never stored in the shortcut.

Old behavior
management detour
  1. 1Manage connectionsLeave the shortcut goal behind.
  2. 2Add or manage API keysSelect provider and save key.
  3. 3“Create a model shortcut now?”Optional setup is attached to credential management.
  4. 4Name model shortcut or skipNo first run completes the journey.

Mental model risk: placing shortcut creation after key setup can make the credential feel model-bound.

New behavior
provider → model → shortcut
  1. 1Add a provider with an API keyOnly providers missing a credential are offered.
  2. 2Validate and save provider keyStored once in the native vault.
  3. 3Choose one provider modelUses the validated model list without relisting.
  4. 4Save shortcut, then run itThe shortcut stores only provider/model identity.

Improvement: the durable sequence mirrors reality: provider access first, reusable target second.

Credential: native vault, provider-scopedShortcut: aliases.json, provider + model only

07 / Cancellation and partial success

Cancellation now respects what has already been saved.

The flow distinguishes aborting an untouched form from stopping after a durable write. Users are told exactly what completed and what did not.

Old behavior
one generic abort idea
cancellation
Escape / Ctrl-C ↓ Was anything saved? Should this be retried? Did generation run? The route does not teach the boundary.

Uncertainty: optional post-actions make it harder to infer which state survives an interruption.

New behavior
explicit durability boundary
Before any write

Exit 130. No credential, no shortcut, no generation.

After key save

Keep the key. Report key-only completion. No generation.

After shortcut save

Keep the shortcut. Exit 0 when its first prompt is cancelled.

After prompt submit

Generate exactly once through the shared output path.

◆ Saved shortcut daily → Codex CLI · fake-model The shortcut was saved, but its first prompt was cancelled; no generation ran.

Improvement: receipts mark the commit points, and later cancellation never rolls them back.

08 / Information architecture

Creation, execution, and connection management each own one job.

The new architecture removes shortcut side effects from connection management and save side effects from one-off execution.

Old behavior
overlapping ownership
Choose modelRun work, then maybe create an alias.
Manage API keyAdd/replace/delete a key, then maybe create a shortcut.
Saved shortcutRun an existing target.

Overlap: two unrelated routes can create reusable configuration.

New behavior
one owner per outcome
Run savedSelect a known shortcut, collect one prompt, run.
Create shortcutConnect if necessary, choose target, name, save, first run.
Run onceSelect target, collect one prompt, run, exit without saving.
Manage connectionsDiscover providers or add/replace/delete API keys.

Improvement: every top-level label describes both its main action and its persistence behavior.

Terminology remains scoped: shortcut in UI, alias in CLI/storage.Direct invocation remains unchanged.

09 / Safety and concurrency

The happy path is clearer—and the failure path is safer.

The branch also hardens the invisible boundaries: generated secrets never reach stdout, and provider credentials cannot be mutated concurrently through separate config roots.

Old behavior
best-effort boundaries
failure cases
model response: prefix API-KEY suffix → response reaches stdout two config roots: write A ─┐ write B ─┴─ same native vault record

Risk: terminal control sequences can hide a secret from raw matching, and config-scoped writes do not serialize a user-global vault.

New behavior
fail closed
failure cases
model response contains a registered credential generation: response withheld stdout: 0 bytes user-wide provider lock: write A ── active owner ── release write B ── waits ───────── acquire

Improvement: raw and terminal-rendered responses are checked, while owner-aware locks serialize add, replace, and delete.
