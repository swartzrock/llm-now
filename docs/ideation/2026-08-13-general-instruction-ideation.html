General instruction for every alias

Add a deliberate, manually edited preamble in config.toml while retaining --instruction as its request-scoped override. The preamble governs saved aliases, precedes each alias’s local instruction, and can be temporarily replaced without discarding that alias specialization.

What the repository makes possible

Grounding Context

Closed, unified configuration

config.toml accepts only version, voice, and aliases at the root today. A general instruction therefore needs an explicit schema home.

One proven composition seam

All generation routes converge immediately before runtime generation. That boundary already chooses one effective instruction and can instead compose two layers once.

Provider-neutral transport

BYOK Runtime already receives one opaque instructions string and maps it to provider-native roles or fields. No provider-specific layer model is needed.

Full-file rewrite risk

Shortcut saves canonically reconstruct the entire document. Unless the new root value participates in every parse, mutation, and serialization path, an ordinary alias save can erase it.

Persistent and temporary intent already have doorways

llm-now --config-path reveals the durable configuration, while --instruction already carries exact request-scoped text. The design can give each surface one layer to own.

Layering precedent converges

Codex, Claude, Copilot, and Gemini all distinguish persistent general guidance from more specific layers. Their shared lesson is ordering and transparency—not a claim that later prose can force an override.

1.

Literal two-layer alias envelope

Invocation scope & compositionConfidence 95%Complexity Medium

Description: Define one optional root shared_instructions value as shared guidance for saved aliases. Whenever a positional alias, --alias, launcher choice, or voice route resolves an alias, use --instruction when supplied or the configured root value otherwise, then append that alias’s optional local instructions. The command-line value replaces only the general layer for one request; it does not erase alias specialization or mutate config.toml.

Basis
direct: --instruction already preserves exact request-scoped text across selection surfaces, saved aliases and explicit selections are distinct in src/args.ts, and src/app.ts converges immediately before generation. external: Claude’s explicit append-versus-replace distinction supports naming which layer the option replaces.
Rationale
This keeps the selected alias envelope while restoring a useful escape hatch. For aliases, the contract is compose(parsed.instruction ?? config.shared_instructions, alias.instructions); for explicit provider/model calls, the configured alias preamble does not apply, but a supplied --instruction remains a valid one-shot instruction.
Downsides
The word “override” must be documented precisely: it replaces the configured general layer, not the alias-specific tail. Users must still avoid contradictions between the effective general text and alias text.
2.

Configuration conservation law

Config representation & round-tripConfidence 96%Complexity Medium

Description: Treat every shortcut save as “change one alias while conserving document-level policy.” The global instruction lives in the full config document, preserves its exact accepted text and omission state through every canonical rewrite, and remains outside the authority of alias creation or overwrite flows. Legacy migration produces absence, never an inferred shared policy.

Create or update

→
Canonical rewrite
global value unchanged
Basis
direct: Alias mutation and serialization currently reconstruct the whole document from recognized fields, and the configuration guide warns that saves may rewrite the file.
Rationale
Manual configuration is only credible when routine shortcut maintenance cannot erase it. This turns preservation from an implementation detail into an observable durability promise.
Downsides
Comments and custom formatting still disappear under the existing canonical rewrite policy. Exact semantic preservation needs broad round-trip coverage across mutation and migration paths.
3.

Backward-compatible version-1 preamble

Config representation & round-tripConfidence 86%Complexity Low

Description: Extend the current schema with one optional root scalar while retaining version = 1. Use the existing instruction validator: present values must be nonblank, accept ordinary multiline text, and reject unsupported controls. Place the field after version in canonical output so the file reads from shared posture to specific aliases.

version = 1
shared_instructions = """Be concise and explicit.
Distinguish facts from assumptions."""

[aliases.reviewer]
provider = "openai"
model = "gpt-5"
instructions = "Focus on correctness and regressions."
Basis
direct: The root schema is closed but already models optional fields; older binaries reject unknown root fields rather than silently ignoring them. Alias instruction validation already matches the value’s type and safety needs.
Rationale
An optional scalar is the smallest schema expression of a document-wide preamble. A version bump would add migration and compatibility ceremony without enabling a different representation.
Downsides
Older releases will reject a v1 file containing the new field even though the version number still matches. If the project defines versions as exact readable field sets across releases, v2 is the more semantically honest alternative.
4.

Request-scoped preamble substitution

CLI precedence & compatibilityConfidence 94%Complexity Low–Medium

Description: Retain --instruction <text> as the temporary source for the general layer. On an alias invocation it replaces config.toml’s root instruction for that request, after which the alias-specific instruction is still appended. On an explicit provider/model invocation there is no configured alias preamble, so the option remains the complete one-shot instruction. It never changes the file.

Basis
direct: The option already spans every selection form, validates exact nonblank text, and reaches the same effective-instruction seam. The required semantic change is narrower than removal: substitute it for the new global source before composing the alias tail.
Rationale
Persistent policy and temporary intent stop competing: config.toml owns the default, the command line owns a one-run substitution, and the alias continues to own specialization. Existing users retain the shipped CLI capability.
Downsides
This changes current behavior for aliases: today the option replaces saved alias instructions entirely; under this direction it replaces only the global layer and preserves the alias tail. Help and tests need an exact precedence table.
5.

Provider-neutral privacy envelope

Invocation scope & transportConfidence 93%Complexity Low–Medium

Description: Preserve the winning general source—request-scoped CLI text or configured root text—and the alias instruction separately through selection, compose once at the final application seam, and give BYOK Runtime the same single opaque instruction it receives today. Provider adapters remain layer-blind. Failure handling registers and redacts the final combined value so neither source nor its composed transport representation appears in diagnostics.

Basis
direct: Runtime accepts one optional instruction and owns native translation plus failure redaction. external: OpenAI, Anthropic, and CLI providers expose different native roles or fields, which makes upstream composition the stable abstraction boundary.
Rationale
One seam gives every provider identical behavior without widening runtime APIs or duplicating precedence logic. Reusing the active-instruction redaction contract contains the privacy blast radius.
Downsides
The combined string may be longer and changes prompt-cache prefixes when the global value changes. Tests must cover raw, escaped, and transport-escaped diagnostic forms.
6.

Conflict and blast-radius contract

CLI transition & compatibilityConfidence 91%Complexity Low

Description: Document ordering precisely without promising impossible semantics: the configured root text—or its one-request CLI replacement—is earlier and general; alias text is later and more specific; conflicting prose remains a user configuration problem rather than a mechanical override. Put the shared field beside the manual-edit workflow and state that changing it is a fleet-wide deployment to every saved alias on its next invocation.

Behavioral warning

“Later” means position, not guaranteed authority. Keep shared and alias instructions compatible.

Basis
direct: Every command reloads configuration, so one edit immediately changes every in-scope alias. external: layered-instruction systems publish priority and explicitly advise against conflicting sources.
Rationale
The largest usability risk is not finding the field; it is underestimating its scope or assuming model behavior has strict CSS-like precedence. A concise contract prevents both surprises.
Downsides
Documentation cannot prevent all contradictory prompts, and the tool cannot reliably detect semantic conflicts without becoming a prompt analyzer.
