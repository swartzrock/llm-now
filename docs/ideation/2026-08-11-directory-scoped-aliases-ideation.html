Directory-scoped aliases

A directory can decide whether an alias is available everywhere. It can only become model execution context for process-backed agents—today, Codex and Claude—not for Ollama, LM Studio, or cloud HTTP APIs.

What the evidence changed

Grounding Context

Core correction: Ollama and LM Studio behave like cloud providers with respect to cwd. They are local HTTP servers, but locality does not give an HTTP generation request a working directory. Directory scoping is still useful for their alias visibility; it just does not add repository context to inference.

Current alias contract

  • Aliases are stored globally under XDG/home/APPDATA and are explicitly available from every working directory.
  • A strict alias record carries only provider, model, and optional instructions.
  • Resolution and generation currently forward no cwd or directory list.

Runtime leverage point

  • The installed runtime’s Codex and Claude classes internally accept cwd.
  • The public factory drops cwd, so both currently fall back to an OS temporary directory.
  • The runtime boundary—not provider discovery—is the place to add process execution context.

Persistence constraints

  • Exact-key versioned validation means directory fields require explicit schema and migration work.
  • Absolute paths are machine-specific and do not belong casually in a portable global target record.
  • Current locking, atomic writes, permissions, and fail-closed conflicts are worth preserving.

External precedent

  • Codex uses cwd to anchor project instructions and command execution.
  • Claude uses cwd as a project boundary and supports explicit additional directories.
  • One primary directory plus explicit extras is stronger precedent than an undifferentiated directory list.

The surviving directions

Ranked Ideas

The first idea is the durable product model. The sixth is a deliberately smaller way to validate the CLI behavior before committing to persistent multi-root configuration.

  1. Capability-checked multi-directory workspace
  2. One active scope root plus explicit extras
  3. Identity-preserving visibility policy
  4. Project enrollment with user-owned targets
  5. Explainable launch plan and preflight
  6. Invocation-bound CLI workspace as v1
1.

Capability-checked multi-directory workspace

Top pickProvider execution contextConfidence 94%Complexity Medium

Keep every alias permanently tied to one provider, model, and optional instruction set. Add one optional workspace containing a primary directory plus zero or more additional directories. Runtime adapters declare whether they can honor a primary cwd and additional roots; unsupported workspace configuration fails clearly instead of being ignored. The alias remains globally callable—this direction introduces no availability or visibility policy.

Basis
direct: The runtime creates URL/model configs for Ollama and LM Studio, while only the internal CLI classes possess cwd. external: Codex and Claude document cwd-based project behavior.
Rationale
This adds the requested project context without changing alias identity or introducing path-dependent visibility. Capability ownership remains explicit and extensible at the runtime boundary.
Downsides
One primary directory is still required because a process has one cwd. Additional-root semantics differ by CLI, so configuration may be valid for Claude before the Codex adapter can honor the same full workspace.
2.

One active scope root plus explicit additional roots

Path matching and multi-directory scopeConfidence 90%Complexity Medium

Treat a configured root set as OR membership: the alias works from any listed root and its descendants. At invocation time, exactly one match is active; the actual invocation directory remains the primary CLI cwd so nested-package context is not discarded. If the desired meaning is “use several roots simultaneously,” model that separately as explicit additional roots, access-only by default and capability-gated per adapter.

Basis
external: Claude exposes one cwd plus explicit added directories; Codex anchors its project instruction walk at the selected cwd. reasoned: OR membership and simultaneous context answer different user intents and should not share one array.
Rationale
This gives “one or multiple directories” a predictable answer across monorepos and adjacent repositories while preserving the caller’s precise subdirectory.
Downsides
Canonicalization and symlink behavior need a crisp rule. Claude has documented extra-root support; Codex should not be presented as equivalent until the adapter has a supported mechanism.
3.

Identity-preserving visibility policy

Alias visibility and precedenceConfidence 88%Complexity Medium

Keep one canonical global alias target and attach an optional allowed-root set. The current cwd filters eligibility; it does not create a second same-named target in every project. An absent policy preserves today’s everywhere-available contract. This supports Ollama, LM Studio, and cloud aliases honestly because visibility is launcher behavior rather than provider behavior.

Basis
direct: Alias names already canonicalize case-insensitively and conflicting targets fail closed. The launcher and deterministic path both load one global document.
Rationale
Filtering one identity avoids the trust cost of path-dependent shadowing: review never quietly becomes a different provider/model merely because the shell moved.
Downsides
Teams that explicitly want project-local definitions cannot reuse the same bare name for distinct targets; that can remain a later, qualified-scope feature if demand emerges.
4.

Project enrollment with user-owned targets

Persistence and portabilityConfidence 80%Complexity Medium

For a team-shareable variant, let a project-local overlay enroll logical alias names and relative workspace metadata while provider/model/instructions remain in each user’s global store. The project says “these workflows apply here”; the user still decides which private target fulfills each workflow. Machine-specific absolute bindings, when unavoidable, live in a user-local overlay rather than committed project data.

Basis
direct: The current record is credential-free but user-global and exact-key validated. reasoned: Separating portable project membership from private target configuration prevents coworkers’ home paths and provider choices from leaking into shared config.
Rationale
This is the most promising collaborative extension if the feature should work across clones, worktrees, or team machines.
Downsides
It introduces a second configuration surface and missing-reference states. It should follow—not precede—proof that personal directory scopes are valuable.
5.

Explainable launch plan with fail-closed preflight

Safety and diagnosticsConfidence 91%Complexity Medium

Resolve a scoped alias into one inspectable launch plan: matched scope, winning policy, provider capability, actual CLI cwd, additional roots, and every ignored or unsupported effect. Feed that same object into generation and an explain command. Before process launch, canonicalize and validate paths; a missing or moved root fails clearly and never degrades to the runtime’s temporary cwd.

Basis
direct: Current alias handling already fails closed on invalid state, and diagnostics are sanitized, redacted, and bounded. The installed CLI runtime otherwise silently chooses a temporary cwd when none is provided.
Rationale
For coding agents, a successful run in the wrong directory is more dangerous than an obvious error. A single plan also prevents explanation and execution from drifting apart.
Downsides
Full local paths may reveal personal filesystem structure, so normal output should prefer logical labels and bounded/redacted paths, with explicit verbose detail.
6.

Invocation-bound CLI workspace as a small v1

Provider execution contextConfidence 89%Complexity Low

Before designing persistent directory profiles, add an explicit workspace mode for Codex and Claude aliases that forwards the invocation cwd through the runtime boundary. Keep current global aliases unchanged. Label Ollama, LM Studio, and cloud aliases as directory-agnostic for execution; they receive no cwd. This is a low-schema-risk way to validate whether correct CLI project context creates enough value to justify the larger scope system.

Basis
direct: The concrete defect is already visible: CLI classes accept cwd internally, but the public factory cannot receive it and defaults to a temporary directory. No alias schema change is required to test explicit invocation-bound behavior.
Rationale
It fixes real Codex/Claude context today and gathers product evidence before choosing overlay, workspace-profile, or schema-v3 persistence.
Downsides
It does not yet make an alias available only in selected roots or preserve a multi-directory profile. Invocation cwd also remains ambient unless the mode is explicit and visible in diagnostics.

What did not survive

Rejection Summary

Sound sub-parts were frequently folded into stronger combined directions. Weak candidates mostly introduced Git-only assumptions, path-dependent target shadowing, or a second configuration system before demand was established.
