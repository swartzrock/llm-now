Codebase Context

Grounding Context

The command namespace belongs to users

Bare positional words—including help, version, and run—are intentionally valid aliases. A new positional aliases command would create a compatibility collision.

A canonical read model already exists

loadAliases() lowercases names, collapses equivalent case variants, preserves provider/default semantics, and fails closed when variants point to different targets.

The streams already have a contract

Successful data belongs on stdout; interactive UI and diagnostics belong on stderr. Invalid configuration already returns a nonzero exit with a config: diagnostic.

Inspection can be an early operation

Help and version return before prompting, discovery, model listing, or generation. Alias inventory can use the same conceptual boundary and remain useful while providers are unavailable.

External CLI precedent is consistent: human-friendly lists and explicit machine output are separate concerns, while a public JSON interface should be versioned independently from internal persistence. The important local exception is LLM-Now’s intentionally open positional alias namespace.

Evidence and sources

  • src/args.ts and tests/args.test.ts — parser modes and positional-alias compatibility.
  • src/aliases.ts — storage schema, canonicalization, and fail-closed loading.
  • src/app.ts and src/prompts.ts — early modes, stream handling, and friendly target rendering.
  • GitHub CLI formatting and kubectl conventions — explicit human and machine output paths.
  • Terraform JSON format — an independently versioned public machine contract.
  • POSIX utility conventions — stdout data, stderr diagnostics, and exit status.

1

Invocation syntax and discoverability

1. --aliases alias inventory

Description: Use the standalone --aliases option to print every configured alias with three values: alias name, provider name, and model. It becomes a peer of help and version: explicit, discoverable, non-generating, and unable to seize a positional word a user may already invoke as an alias.

Rationale
The exact invocation is settled and the default result answers the complete inspection question without spending the positional namespace or forcing anyone to rename an existing alias.
Confidence
98%
Complexity
Low
Meeting test
llm-now --aliases prints alias, provider name, and model while an existing positional alias named aliases remains invocable.

Basis — direct: tests/args.test.ts:100-107 intentionally preserves bare help, version, and run as alias names; README.md:67-71 already describes explicit options as the safe answer to future name ambiguity.

Downsides: A flag is less conventionally extensible than an aliases list/show command family. Any future filtering or alternate formats should remain subordinate to this simple default behavior.

2

Human versus machine output modes

2. Two honest views of one inventory

Description: Give people a compact roster of alias, provider, and model, while offering an explicitly requested JSON view for programs. The roster can use friendly provider labels and “provider default”; JSON keeps canonical provider IDs and literal null. Format follows explicit intent, never whether stdout happens to be a TTY.

Human roster

fred → Ollama · llama3.1
codex → Codex CLI · provider default

Machine view

Canonical IDs, explicit fields, literal nulls, no headings or display phrases mixed into the data.

Rationale
Humans scan labels and relationships; scripts need semantic fields immune to alignment, color, and copy changes.
Confidence
93%
Complexity
Medium
Meeting test
The same explicit machine invocation produces the same parseable shape in a terminal, redirected, and under CI.

Basis — direct + external: src/prompts.ts:148-154 already distinguishes friendly provider/model rendering from stored values, and README.md:80 establishes stdout as the data stream. GitHub CLI and kubectl make machine formats explicit rather than asking scripts to scrape default presentation.

Downsides: Two views create a parity obligation and slightly more documentation and testing. A JSON-only design is simpler, though less pleasant for routine terminal inspection.

3

JSON data contract and evolution

3. Public canonical alias manifest

Description: Publish a small inspection contract independent of the on-disk v1 document: a format version plus an ordered array of canonical {alias, provider, model} records. The output reflects the namespace LLM-Now actually resolves after lowercasing and benign legacy-variant collapse, while preserving model: null as provider-default selection.

{
  "formatVersion": "1.0",
  "aliases": [
    { "alias": "codex", "provider": "codex-cli", "model": null },
    { "alias": "fred", "provider": "ollama", "model": "llama3.1" }
  ]
}
Rationale
Automation should depend on a consumption-oriented interface, not internal file layout, insertion order, or legacy spelling artifacts.
Confidence
91%
Complexity
Medium
Meeting test
Internal storage can evolve without silently changing what current inventory consumers interpret.

Basis — direct + external: src/aliases.ts:80-103 makes persistence a strict closed schema, while src/aliases.ts:110-146 creates the canonical resolver view. Terraform’s public JSON format demonstrates independent versioning and explicit compatibility semantics.

Downsides: A separate versioned contract costs more than dumping the file, and an array requires scanning for exact lookup. It also creates a promise that future output changes must honor.

4

Safety, determinism, and automation behavior

4. Offline atomic configuration snapshot

Description: Define inventory as an offline read of configured routing—not a provider health check. It consumes no prompt, performs no provider discovery, model listing, credential validation, or generation, and produces either one complete canonical snapshot or no payload. A missing store is a successful empty inventory; corrupt or conflicting state leaves stdout empty, writes the configuration diagnostic to stderr, and exits nonzero.

Rationale
Voice routers, completion systems, and audits need trustworthy configured targets precisely when runtimes or networks may be unavailable.
Confidence
97%
Complexity
Low–Medium
Meeting test
With closed stdin and broken providers, valid configuration still lists; ambiguous configuration never leaks partial records.

Basis — direct: src/app.ts:659-691 and tests/app.test.ts:199-238 show early modes can avoid runtime operations. src/aliases.ts:106-169 distinguishes missing storage from invalid/conflicting storage, and src/app.ts:709-716 already routes configuration failures to stderr with exit 1.

Downsides: The executable currently constructs some dependencies eagerly, so “offline” should promise no runtime operations rather than literally zero initialization. The result intentionally says nothing about provider reachability.

5

Safety, determinism, and automation behavior

5. Byte-stable JSON snapshots

Description: Go beyond “valid JSON” and make unchanged logical alias state produce identical bytes: canonical alias ordering, stable record field order, literal nulls, and one final newline. Benign differences in legacy key casing or file insertion order disappear from the published snapshot.

Rationale
Stable bytes make change detection, fixture tests, caches, and generated voice menus dependable and cheap.
Confidence
84%
Complexity
Low
Meeting test
Two stores with the same resolved namespace produce byte-identical successful JSON.

Basis — direct: src/aliases.ts:110-146 already sorts during canonicalization, and tests/aliases.test.ts:112-156 requires conflict behavior to be independent of source order. A public serializer can extend that determinism to successful output.

Downsides: Byte stability constrains otherwise harmless serializer changes, and many JSON consumers should compare parsed values rather than raw bytes. It is leverage for tooling, not a prerequisite for basic enumeration.
