Ideation · terminal entry experience

Make bare llm-now feel like a launchpad

The current no-input screen asks users what they want to “set up,” then mixes runnable shortcuts with provider discovery and credential administration. The better organizing principle is intent: help people start work, choose something new, or deliberately enter management.

Grounding

Codebase Context

The existing product already contains most of the interaction pieces needed for a stronger entry experience. The problem is primarily how the bare command routes and frames them.

The root mixes unlike things

runSetup alphabetizes saved aliases, then appends provider discovery and API-key management to the same autocomplete under “What would you like to set up?”

Selections stop too early

An alias selection prints a second command and exits. Discovery selects only a provider, then returns a template with --model <id>.

The complete flow already exists

Prompt-bearing interaction already offers aliases first, supports provider/model selection, generates, optionally saves a shortcut, and prints reuse guidance.

The terminal contract is strong

Prompts and guidance stay on stderr while the model response stays on stdout. Discovery is passive, cancellation exits 130, and credentials never belong in selectable UI data.

Recommendation

Use Idea 1 as the information architecture, and Idea 2 as the behavioral contract. In plain terms: show an adaptive work-versus-management home, then ensure every successful branch finishes the task before teaching the reusable command.

Idea 1 · recommended

Adaptive two-door home

Confidence 92% Complexity Medium State · intent · presentation

Description: Preserve two stable concepts—work and management—while changing their emphasis using already-known state. A returning user sees “Run with a saved shortcut” first and “Manage connections and shortcuts” second. A user with no shortcuts sees “Choose a model to use” first and “Connect or manage providers” second. Each route opens a homogeneous searchable picker; provider discovery runs only after the user chooses a route that needs it.

Conceptual shape: use known alias state to choose emphasis; do not perform eager provider scans just to render the home.

Axis
User state, intent hierarchy, and choice presentation.
Basis
direct: Alias state is already known; the prompt-bearing path already contains focused alias and provider/model pickers; the current mixed root is assembled in one runSetup seam. external: OpenCode and Claude Code both separate operational use from connection or management work.
Rationale
Newcomers get a clear next step, returning users regain a fast daily path, and the interface achieves real hierarchy without needing unsupported section headings inside one fuzzy list.
Downsides
Some actions gain one navigation step. The zero-shortcut copy must distinguish “choose something already available” from “connect something new” without pretending readiness is known before discovery.

Idea 2

One invocation, then teach

Confidence 95% Complexity Medium Selection outcome

Description: Make “no successful launcher branch asks for a second invocation” a product invariant. Selecting an alias collects a prompt and generates. Discovery continues through model choice and prompt capture. Only after success does stderr show the exact reusable command or saved alias.

The command template becomes a receipt for a completed action instead of a substitute for the action.

Axis
Selection outcome.
Basis
direct: Both current dead ends can compose steps already used by the normal interactive flow. The application already sends model output to stdout and all interactive guidance to stderr.
Rationale
This removes the most surprising behavior in the screenshot while retaining the CLI’s teachability and pipeline-safe output contract.
Downsides
Bare invocation can now cross into a billable generation. The UI needs an unmistakable prompt-entry and execution boundary, plus clear cancellation before the request is sent.

Idea 3

First useful result onboarding

Confidence 89% Complexity Medium State · outcome

Description: When no shortcut exists, guide the user through provider and model choice far enough to run a first prompt, then offer to name that target. If passive discovery finds nothing, switch to a focused recovery screen that explains what was checked and offers relevant connection actions. The first session succeeds when the user receives a result; onboarding becomes durable when the first shortcut is saved.

Immediate value and durable setup are two milestones in one guided path, not competing definitions of completion.

Axis
User state and selection outcome.
Basis
direct: Empty alias state, passive no-provider diagnostics, provider/model selection, generation, and post-generation alias saving all exist today.
Rationale
New users should not have to understand the provider inventory before receiving value, and setup should leave behind a reusable target rather than abstract knowledge.
Downsides
The combined path is longer and needs clear backtracking. Connection failures must remain honest recovery states rather than being papered over with a recommended provider.

Idea 4 · alternative ordering

Prompt-first launcher

Confidence 74% Complexity Low Intent · outcome

Description: Ask “What would you like to ask?” immediately, then resolve the execution target using saved shortcuts first and a fresh-model escape hatch. This is the strongest alternative to an intent gate: it assumes a bare LLM command is primarily for doing LLM work and defers provider plumbing until it becomes necessary.

CURRENT
$ llm-now

What would you like to set up?
  deepseek32
  haiku
  Discover providers…
  Add or manage API keys…
PROMPT-FIRST
$ llm-now

What would you like to ask?
› Summarize this branch

Use a saved shortcut
  haiku · Claude CLI
  local · Ollama
  Choose another model…
Axis
Intent hierarchy and selection outcome.
Basis
direct: Prompt and target resolution are separable stages in the current application. reasoned: A user typically knows the job before knowing the provider/model plumbing.
Rationale
The product’s purpose becomes obvious at first contact, and the model inventory becomes a means rather than the main event.
Downsides
Users who opened the command to manage a connection need a visible escape hatch. Typing a prompt and then canceling during model choice can feel like lost work. This ordering should be compared directly with Idea 1, not stacked blindly on top of it.

Idea 5

Dedicated llm-now setup entrance

Confidence 78% Complexity Medium Intent hierarchy

Description: Give provider discovery, API-key work, and future shortcut administration a stable explicit command. Keep “Setup and connections…” discoverable from the bare launcher, but stop forcing high-frequency work and sensitive maintenance to share the same undifferentiated front door.

DAILY ENTRANCE
$ llm-now

Run with a shortcut…
  Choose another model…
  Setup and connections…
ADMINISTRATIVE ENTRANCE
$ llm-now setup

Connections & shortcuts
  Discover available providers…
  Add or manage API keys…
  Manage saved shortcuts…
Axis
Intent hierarchy.
Basis
direct: Credential management is already a deliberate multi-step flow with materially different risk from choosing a saved alias. reasoned: Daily traffic and maintenance traffic deserve stable, distinct addresses.
Rationale
This gives low-frequency controls a durable home and prevents the bare launcher from becoming a dumping ground as management features grow.
Downsides
It introduces another command to learn. It complements a good bare home but does not remove the need to make setup discoverable and state-aware there.

Idea 6

Hundred-shortcut palette

Confidence 88% Complexity Low Choice presentation

Description: Design as if a power user has one hundred aliases. The root contains “Search saved shortcuts…” rather than every alias; selecting it opens a dedicated type-to-filter list with provider/model hints. The extreme case reveals the current structural flaw even when the screenshot contains only four aliases.

FLAT ROOT · GROWS FOREVER
  alias-001
  alias-002
  alias-003
  …
  alias-100
  Discover providers…
  Add or manage keys…
BOUNDED ROOT
  Search saved shortcuts…
  Choose another model…
  Manage connections…

then: type to filter 100 shortcuts
Axis
Choice presentation.
Basis
direct: The current root grows linearly by concatenating every alias with navigation actions, while the existing autocomplete already filters deterministically. reasoned: A collection is data to search, not navigation to flatten.
Rationale
The launcher stays calm as users accumulate targets, and every screen contains one kind of selectable thing.
Downsides
Users with only a handful of aliases pay an extra Enter. Avoid a speculative recency system; deterministic sorting and explicit search are already trustworthy.

Idea 7

Readiness telemetry

Confidence 76% Complexity Low Choice presentation

Description: Separate state from controls. A compact status line explains why this screen looks the way it does—“Ready · 4 saved shortcuts” or “No saved shortcut yet”—then every row begins with an action verb. Alias is the user-owned concept; provider/model appears as supporting detail. Safe provider capability can appear after discovery, but secret values never do.

READY · 4 SAVED SHORTCUTS

› Run with haiku
  Claude CLI · provider default
  Run with local
  Ollama · llama3
NO SAVED SHORTCUT YET

› Choose a model to use
  Connect or manage providers
  Discovery runs only when chosen
Axis
Choice presentation.
Basis
direct: Alias counts are known, alias rows already carry provider/model hints, and runtime connection state can be reported without placing credentials in prompt data.
Rationale
Users no longer have to infer readiness from an assorted list, and action-led labels make the outcome of each row predictable before Enter.
Downsides
Provider readiness may require discovery latency. The initial status should rely only on already-known state unless the user deliberately enters a discovery route.

What did not survive

Rejection Summary

Most cuts were consolidations: several independent frames converged on the same stronger direction. Two ideas were rejected on evidence rather than taste.
