What reality permits

Grounding Context

Feasibility answer: SVGs from SVGL cannot render directly in this application’s current terminal surface. True images are possible only through emulator-specific bitmap protocols such as Kitty Graphics, iTerm2 Inline Images, or Sixel, each with detection, placement, and fallback costs.

Character-cell UI

The CLI uses @clack/prompts and ANSI styling on stderr. Its local option contract is only value, label, and optional hint; there is no per-row image or right-side renderer.

Identity is already centralized

PROVIDER_LABELS distinguishes anthropic → Anthropic from claude-cli → Claude CLI. The former is a cloud API-key provider; the latter is an authenticated local CLI route.

State transitions are more valuable than decoration

Keys are validated before saving, but later menus mostly return to bare provider labels. Model-list failures remove the selected provider and continue, which can erase useful recovery context.

Vendor marks create an asset policy

SVGL’s repository license is not blanket permission for every indexed trademark. The current native release is a lean executable without a logo corpus, renderer, or provenance lifecycle.

The directions worth discussing

Ranked Ideas

The ranking favors useful provider context that works with the existing prompt stack. Exact vendor-logo rendering appears only as a rejected direction because its portability and maintenance costs overwhelm the value of this small surface.

Idea 1 · Top pick

Provider Identity Card + State-Aware Hints

Confidence 95% Complexity Low–Medium

Description: Enrich the existing provider identity map with a canonical connection class and compact terminal-safe copy, while keeping runtime readiness separate. Stock Clack labels and focused-row hints can then distinguish Anthropic · API key, Claude CLI · authenticated CLI, and Ollama · local; a separate status line handles durable selected or validated state.

Axis
Provider identity and selection state
Basis
direct: src/prompts.ts:23–53 already centralizes labels and defines the only supported row fields as value, label, and hint. Provider rows at src/prompts.ts:211–214 currently carry only the label.
Rationale
This solves the user’s recognition problem without implying that Anthropic API access and Claude CLI authentication are the same thing. It also creates one reusable identity seam for provider selection, key setup, model selection, and later additions.
Downsides
A registry can become overbuilt. Immutable identity metadata must remain separate from discovered, validated, saved, and environment-preferred runtime states.

Illustrative direction: identity fans out from one source; live readiness remains owned by each flow.

Idea 2

Verified Connection Passport

Confidence 92% Complexity Low

Description: After a credential is validated—and again after it is saved—render a compact plain-text receipt on stderr: provider, access method, verified state, and credential source, without any secret material. Carry the same identity into the following model or alias step.

Axis
Provider identity and selection state
Basis
direct: src/app.ts:524–542 validates the candidate, asks to save the verified key, persists it, and currently emits only Saved the … API key. Environment precedence is already explained at src/app.ts:485–495.
Rationale
The logo earns attention when it confirms a meaningful lifecycle transition. A truthful text receipt gives the user more value than a decorative mark and remains safe during a sensitive flow.
Downsides
Copy must distinguish “validated,” “saved,” and “active through environment” precisely. Calling discovery or storage alone “ready” would be misleading.

Illustrative sequence: the branded moment comes after verification, not around secret entry.

Idea 3

Text-First Provider Stamp on the Next Prompt

Confidence 88% Complexity Low

Description: Put provider identity where it is already known: in the model prompt or a short line immediately above it. A treatment such as Choose a model · Anthropic / API or Selected Claude CLI · local authentication provides the requested orientation without right-aligning art inside provider rows.

Axis
Prompt layout and right-side placement
Basis
direct: The flow selects a provider before constructing the model picker at src/prompts.ts:210–268. Stock prompt options have no alignment or image field, so the next prompt is the first stable surface with one unambiguous provider.
Rationale
This is the closest low-cost expression of “show the provider on the right”: move identity to the next decision, where only one provider must be shown and ordinary terminal text is sufficient.
Downsides
It does not literally show a corporate logo, and adding too much context to prompt messages can feel verbose. Copy should stay compact and survive narrow terminals.

Idea 4

Failure Annunciator

Confidence 84% Complexity Low

Description: When model listing fails and the chooser removes a provider, preserve a concise provider-aware recovery line before showing the remaining choices: Anthropic unavailable · model listing failed · choose another provider. The same visual grammar can distinguish focused, verified, saved, and temporarily unavailable states.

Axis
Provider identity and selection state
Basis
direct: On model-list failure, src/prompts.ts:224–243 emits a diagnostic, removes the provider from the list, and continues. That behavior can make a transient failure feel like the app forgot the prior selection.
Rationale
Branding becomes operationally useful: it anchors a failure to the provider the user chose and makes recovery comprehensible instead of merely decorative.
Downsides
Error text must not duplicate noisy diagnostics or imply a credential problem when the failure was network- or provider-side. Stale status must be cleared after the next selection.

Idea 5

First-Party llm-now Connection Mark

Confidence 70% Complexity Medium

Description: If the interface still needs a visual accent, use an llm-now-owned, terminal-cell mark followed by an explicit provider code and connection class—for example ◆ ANT · API. The shape belongs to llm-now; canonical provider text carries the meaning; color is supplemental and disappears cleanly under NO_COLOR.

Axis
Terminal rendering capability and portability
Basis
reasoned: Ordinary text cells are the only rendering layer shared by every supported terminal and native target. A first-party mark avoids importing third-party artwork while still creating a recognizable connection moment.
Rationale
This could give llm-now a distinctive visual language: the product remains the owner of the experience while clearly naming the selected provider and transport.
Downsides
A new mark needs design and recognition testing. Provider initials can collide, and the mark cannot be the sole identity because fonts, color, and screen-reader behavior vary.

Idea 6

Vendor-Asset Gate: Ship None Now

Confidence 91% Complexity Low

Description: Make the immediate asset policy explicit: no SVGL or vendor logo files enter the runtime CLI. A future asset must name its source and revision, applicable license and brand review, consuming surface, monochrome/plain-text fallback, and release owner before it can be included.

Axis
Asset packaging, brand provenance, and fallback behavior
Basis
external: SVGL is MIT-licensed as a repository, while its contribution guidance still asks contributors to verify rights for each logo; vendor brand rules add separate trademark constraints. direct: the present runtime has no logo renderer or provider-asset corpus.
Rationale
This prevents “download an SVG” from silently becoming a brand, legal, release-packaging, and update subsystem. It keeps the portable text direction unblocked.
Downsides
A gate can become ceremony if created as a large manifest before any asset is justified. Keep it as a decision rule until a real non-terminal consumer exists.
