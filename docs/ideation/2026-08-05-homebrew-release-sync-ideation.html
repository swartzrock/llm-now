Grounding Context

Codebase Context

llm-now already has the hard part: an exact-SHA, fail-closed release workflow that builds five targets, signs and notarizes macOS artifacts, creates an authoritative SHA256SUMS, publishes attestations, and safely recognizes an already-complete release on rerun. Homebrew should consume that verified public release; it should not become another publisher of release assets or another authority for checksums.

The source repository also already renders the four Homebrew-native combinations—macOS and Linux on ARM64 and AMD64—from a formula template. The problem is ownership drift: the template and the live tap formula differ in headers, description, architecture DSL, and test command. Before automation can own the whole file, those two representations need to converge intentionally.

swartzrock/homebrew-tap is deliberately small and currently has no tap-side CI. Its public default branch already carries llm-now 2.2.0, while the supplied local checkout has stale tracking state. Any implementation must synchronize that checkout first and treat the public branch—not the local ref—as current truth.

Why not simply install Homebrew Releaser?

The action does support Darwin/Linux and AMD64/ARM64 targets, which validates the multi-platform formula shape. But it assumes fixed archive URL patterns, generates and uploads its own checksum file, always selects the latest release, clones and pushes the tap, and asks for a PAT with access to both repositories. Those choices duplicate llm-now's exact-release invariants instead of preserving them.

Non-negotiable boundary

A tap write is a post-publication projection. Its failure may fail the workflow run and demand recovery, but it must never delete, recreate, move, or otherwise invalidate a correct immutable GitHub Release. Rerunning the exact commit reconciles only the missing projection.

Decision surface

Topic Axes

  1. Exact-release handoff and recovery
    When the sync runs, what it trusts, and how an interrupted update safely resumes.
  2. Formula source of truth and template convergence
    How four platform bindings remain byte-for-byte reproducible without two hand-maintained formulas.
  3. Cross-repository authentication and secret boundary
    Which identity can write the tap and how narrowly that authority can be scoped.
  4. Tap mutation and verification path
    Whether updates land as a direct commit or PR, and how stale, conflicting, or newer state is handled.

Idea 1 · recommended

Verified-release materialized-view reconciler

Confidence 91% Complexity Medium

Description: Extend the source-owned release train with a post-publication Homebrew reconciliation step. Whether the run just published the exact release or proved that the exact release already exists and is complete, the reconciler downloads the public release manifest and four Homebrew artifacts, re-verifies them, renders the canonical formula, reads the live tap formula, applies an explicit state transition, and updates only Formula/llm-now.rb with an optimistic GitHub Contents API write.

Axis
Exact-release handoff and recovery
Basis
direct: the existing workflow already models fresh publication and verified-existing-release paths at one exact commit; the renderer already binds all four platform URLs and checksums.
Rationale
The source release knows exactly which immutable assets are authoritative. Reusing its existing recovery path gives immediate updates without inventing a second “latest release” control plane.
Downsides
Adds a cross-repository credential and a narrow amount of custom reconciliation logic. Direct commits also require tap branch policy to permit the automation identity.

State transition contract

The reconciler is not “write whatever was rendered.” It compares the requested exact release with the tap’s parsed state and refuses ambiguity or regression.

Observed tap stateInterpretationAllowed result
Exact generated bytesProjection already completeNo-op success
Older valid versionNormal forward publicationAdvance with current blob SHA
Same version, different bytesManual drift, corruption, or changed generatorFail closed; require review
Newer versionRerun of an older release or out-of-order jobRefuse downgrade
Concurrent modificationContents API blob SHA no longer matchesRe-read once, reclassify, then no-op or fail
Missing or unparseable formulaUnexpected tap shapeFail closed; never synthesize over ambiguity

Direction for llm-now

  • Converge the source formula template with the current tap formula before declaring it canonical.
  • Strengthen renderer tests with golden, byte-level coverage of all four OS/architecture bindings.
  • Run reconciliation after a fresh publish and after the existing exact-release verifier succeeds.
  • Re-download and verify public assets and SHA256SUMS; do not reuse unchecked workspace artifacts.
  • Add the explicit tap state machine, exact-file Contents API update, and manual recovery entry point.
  • Update release-policy tests and releasing documentation to reflect the new post-publication projection.
  • Document setup and rotation for a tap-only secret such as HOMEBREW_TAP_TOKEN.

Direction for homebrew-tap

  • Synchronize the supplied local checkout with public main before implementation.
  • Make Formula/llm-now.rb the exact generated output of the canonical source template.
  • Keep the first convergence semantically equivalent to the current 2.2.0 formula so automation does not smuggle a formula redesign into setup.
  • Add only a concise generated-ownership and recovery note if it materially helps future maintainers.
  • Do not add tap-side CI for this direct-commit direction; validate before the write in the source workflow.
  • If branch rules reject the automation identity, switch deliberately to Idea 6 instead of weakening protection ad hoc.

Failure semantics

A failed tap update leaves a valid GitHub Release and a failed workflow run. The operator reruns the workflow for the same exact commit or invokes its recovery entry point. The release is never recreated, and the tag is never moved.

Idea 2

Canonical formula compiler contract

Confidence 95%Complexity Low

Description: Treat the source repository’s formula template plus exact manifest as a tiny compiler: one canonical, fully styled formula enters; one deterministic tap file leaves. Converge headers, description, Homebrew DSL, install stanza, and test block up front, then prohibit partial substitution or tap-local edits to generated regions.

Axis
Formula source of truth and template convergence
Basis
direct: the existing renderer already performs strict manifest parsing and four target substitutions, while the source and live formula currently drift outside those substitutions.
Rationale
Whole-file determinism makes idempotency, review, recovery, and provenance obvious. It removes the most likely long-term failure: two humans editing two almost-identical formulas.
Downsides
Requires a deliberate one-time convergence decision. Formula copy or style changes thereafter originate in llm-now, not directly in the tap.

Idea 3

Exact-state compare-and-swap tap protocol

Confidence 94%Complexity Low

Description: Define tap mutation as a compare-and-swap operation over the live file’s blob SHA and semantic version, not as a blind clone/edit/push. Exact bytes no-op; older advances; same-version drift, newer state, or malformed state fails; a single concurrent-update reread decides the final result.

Axis
Tap mutation and verification path
Basis
external: GitHub’s Contents API accepts the current file SHA when updating a file, giving the operation an optimistic concurrency guard.
Rationale
A one-file materialized view does not need a checkout and push race. The protocol makes out-of-order reruns and human edits observable instead of silently overwriting them.
Downsides
API diagnostics must be good enough for maintainers to understand refusals. More complex future tap changes would outgrow the one-file mutation model.
4

Idea 4

Tap-only fine-grained writer identity

Confidence 90%Complexity Low

Description: Store a fine-grained personal access token in the source repository, selected only for swartzrock/homebrew-tap with repository Contents write access and the shortest practical lifetime. Use the source workflow’s ordinary GITHUB_TOKEN for all source-repository work and expose the tap token only to the final reconciliation step.

Axis
Cross-repository authentication and secret boundary
Basis
direct + external: GitHub’s workflow token is repository-scoped; Homebrew Releaser itself requires a PAT for cross-repository tap writes, but recommends broader access to both repos than this design needs.
Rationale
For a personal two-repository setup, a tap-only token is the smallest operational mechanism. A GitHub App becomes attractive only if organizational policy, identity lifecycle, or repository count justifies the extra machinery.
Downsides
The credential is tied to a user account and needs expiration/rotation discipline. Protected-branch rules may require explicit bypass permission or a PR-based variant.

Idea 5 · best no-shared-secret alternative

Zero-shared-secret tap pull reconciler

Confidence 86%Complexity Medium

Description: Put a scheduled and manually dispatchable workflow in the tap. It queries the public llm-now release, verifies the exact tag and assets, renders the same canonical formula, applies the same state machine, and commits with the tap repository’s own workflow token.

Axis
Cross-repository authentication and secret boundary
Basis
reasoned: public release data needs no source credential, while a workflow running inside the tap naturally receives write authority scoped to that tap.
Rationale
It eliminates the only shared secret and cleanly assigns ownership to the repository being mutated. This is the strongest alternative when credential policy outweighs immediate publication.
Downsides
Scheduled runs introduce lag, and the renderer or formula contract must be copied, fetched, or packaged across repositories. A manual source-to-tap dispatch restores immediacy but reintroduces cross-repository authentication.
6

Idea 6 · protected-branch variant

Reviewed generated-formula promotion lane

Confidence 82%Complexity Medium

Description: Have the source reconciler create or refresh a deterministic tap pull request instead of committing directly. Tap checks verify the generated formula and installation behavior; maintainers merge manually at first, with auto-merge as a separate policy decision later.

Axis
Tap mutation and verification path
Basis
external: tools such as GoReleaser’s Homebrew publisher use pull requests as a supported tap-promotion model when direct writes are undesirable.
Rationale
It aligns with strict branch protection and gives formula changes a human-readable audit surface. Deterministic branch and PR identity can keep reruns idempotent.
Downsides
A PR is another lifecycle to reconcile and delays “updated whenever released” unless auto-merge is enabled. Auto-merge adds check design and branch-policy work that the current minimal tap does not otherwise need.
